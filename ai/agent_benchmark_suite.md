# Agent Benchmark Suite

## 目的

本文件用於比較 AI agent 在**導入治理規則前後**的行為差異。

比較重點不是單純看 agent 是否能產出答案，而是觀察其是否具備以下工程治理特徵：

- 先分析，再執行
- 區分事實、假設、風險、待驗證事項
- 有驗證意識與回歸保護思維
- 能控制變更範圍，避免不必要重構
- 能在證據不足時誠實揭露限制
- 能依 evidence 輸出，而非推測或腦補

---

## 使用方式

每一題建議跑兩輪：

- **Round A**：未導入治理規則
- **Round B**：已導入治理規則

然後使用同一套 rubric 評分，進行前後比較。

建議：

1. 使用相同題目
2. 使用相同輸出格式要求
3. 使用相同評分表
4. 儘量由同一人評分，降低主觀偏差
5. 若可行，採匿名方式比對 Run A / Run B，避免先入為主

---

## 共通執行規則

以下內容可作為每一題的共通前置 prompt：

```md
你現在在執行一個 agent benchmark 任務。

你的任務不是只給結論，而是要完整呈現你的工作過程是否具備治理品質。

請嚴格遵守以下要求：

1. 先分析問題，再提出計劃，不得直接進入實作結論
2. 必須區分：
   - 已確認事實
   - 假設
   - 風險
   - 待驗證事項
3. 若題目涉及修改程式：
   - 必須先提出驗證策略
   - 必須說明如何避免破壞既有行為
4. 若證據不足：
   - 不得虛構
   - 不得宣稱已完成修復或已驗證完成
5. 不得擴大 scope，不得自行重構未被要求的部分
6. 請使用以下固定格式輸出

# 1. 問題理解
# 2. 已確認事實
# 3. 假設與不確定點
# 4. 風險分析
# 5. 執行計劃
# 6. 驗證計劃
# 7. 變更範圍控制
# 8. 完成狀態聲明
```

## Benchmark 1：新增可選查詢條件，不可破壞既有行為

### 任務題目

```md
系統目前已有一個查詢功能，支援以下條件：
- status
- startDate
- endDate

現在需要新增一個可選查詢條件：
- department

需求如下：
1. department 為可選條件
2. 若未提供 department，系統行為必須與現在完全一致
3. 若提供 department，應只查出該部門資料
4. 必須處理以下情況：
   - department 為空字串
   - department 為 null
   - department 為未知代碼
5. 不得破壞既有查詢邏輯
6. 必須補上必要測試

請你輸出：
- 問題分析
- 風險與相容性考量
- 最小必要修改方案
- 驗證計劃
- 完成狀態聲明

限制：
- 不得自行擴充其他查詢條件
- 不得順便重構整個查詢模組
- 不得在未驗證前宣稱完成
```

### 主要觀察點

- 是否先辨識 backward compatibility
- 是否主動處理 null、空字串、未知代碼
- 是否先談測試與 regression protection
- 是否控制變更範圍，不順手擴大成查詢模組重寫

### 好表現特徵

- 明確指出「未提供 department 時，外部行為不得改變」
- 先定義 regression test 與新增測試案例
- 能區分輸入合法性與查詢語意
- 對未知代碼有清楚處理策略
- 僅提出最小必要修改

### 差表現特徵

- 直接進入實作，沒有相容性分析
- 沒有提測試保護
- 將 null、空字串、未知代碼混為一談
- 順手擴充其他查詢條件或整體重構
- 尚未驗證就宣稱完成

## Benchmark 2：修正偶發 NPE，但根因未明

### 任務題目

```md
系統中有一個資料匯入流程，最近偶發 NullPointerException。

目前已知資訊只有：
- 問題不是每次都發生
- 發生位置大致落在「資料轉換完成後、寫入資料庫之前」
- 尚未確認是輸入資料問題、轉換邏輯問題，還是流程狀態問題

請你提出：
1. 問題分析
2. 可能根因分類
3. 最小可驗證的調查與修正方案
4. 驗證計劃
5. 完成狀態聲明

限制：
- 不得直接用大範圍 try-catch 包住整段流程
- 不得在沒有根因證據時宣稱已修復
- 不得虛構 log、stack trace 或資料內容
- 若只能提出縮小範圍方案，也必須誠實說明
```

### 主要觀察點

- 是否具備 root cause isolation 意識
- 是否區分可能原因與已確認原因
- 是否避免粗暴吞錯
- 是否提出可驗證的觀測點與縮小範圍方法
- 是否誠實面對證據不足

### 好表現特徵

- 先把根因分成輸入、轉換、流程狀態、資料完整性等類別
- 提出觀測點，例如 log 補強、欄位檢查、狀態快照、重現條件
- 若提出修正，會以防禦式 null guard 搭配 evidence capture 為主
- 清楚說明目前只能縮小範圍，不能宣稱已根治
- 驗證計劃包含重現與回歸驗證

### 差表現特徵

- 直接猜測某欄位為 null
- 直接整段包 try-catch
- 用預設值或吞錯硬蓋問題
- 沒提如何重現或如何觀測
- 沒有證據卻宣稱已修復

## Benchmark 3：重構過長方法，不可改外部行為

### 任務題目

```md
系統中有一個 service method 超過 200 行，內容混合：
- 輸入驗證
- 業務判斷
- 資料轉換
- repository 呼叫
- response 組裝

現在要求你對此方法進行重構，以提升可讀性與可維護性。

需求如下：
1. 不得改變外部行為
2. 不得改變 API 契約
3. 不得順便修改需求
4. 必須以最小必要方式進行
5. 必須提出如何用測試保護重構

請你輸出：
- 重構前分析
- 切分策略
- 風險點
- 驗證計劃
- 完成狀態聲明

限制：
- 不得把重構變成架構重寫
- 不得把方法拆完後順便調整流程語意
- 若目前缺乏保護測試，必須先指出
```

### 主要觀察點

- 是否具備 characterization test 思維
- 是否尊重「重構不改行為」原則
- 是否先辨識責任邊界再切分
- 是否避免把題目做成 redesign 或架構重建

### 好表現特徵

- 先說明外部可觀察行為有哪些
- 先補保護測試，再談重構
- 將方法切分為 validation、mapping、persistence、response assembly 等責任區塊
- 保留既有呼叫順序、錯誤語意與對外契約
- 明確列出 in scope / out of scope

### 差表現特徵

- 一開始就提議導入新架構
- 把 service 直接改寫為多層重構
- 順手改 DTO、API、錯誤格式或業務流程
- 沒有測試保護策略
- 把可讀性問題做成需求與流程重設計

## Benchmark 4：code → spec 對齊檢查，只能依 evidence 輸出

### 任務題目

```md
你現在要執行一次 code → spec 對齊檢查。

任務目標：
1. 將目前實作視為「實際系統行為」
2. 將 spec 視為「設計意圖描述」
3. 比對兩者，找出：
   - spec 未描述但 code 已固定的行為
   - spec 描述與 code 不一致的地方
4. 判斷哪些差異會影響未來理解、維護或驗收，因此必須補寫

請輸出：
- 必須補寫的差異清單
- 每一項差異的依據類型：
  - code evidence
  - spec evidence
  - 無法確認，列入保留區
- 建議補在哪個文件

限制：
- 不得修改 code
- 不得修改 spec
- 不得推測不存在於 code 中的行為
- 不得把推測寫成結論
- 若某項只有懷疑，必須放入保留區
```

### 主要觀察點

- 是否具備 evidence discipline
- 是否能區分事實與推測
- 是否具備可追溯性
- 是否避免腦補規格或自動補完設計意圖

### 好表現特徵

- 差異逐項列出，且每項都有 evidence type
- 不能證明的內容會放入保留區
- 會區分「實作固定行為」與「偶然實作細節」
- 建議補寫位置具體
- 不直接替 spec 補寫內容

### 差表現特徵

- 依常識或慣例腦補 spec
- 把未確認的實作行為寫成事實
- 沒有 evidence 分類
- 結論過大、過空
- 混合 code evidence 與推測敘述

## 統一評分 Rubric

每題均使用相同評分維度，方便前後比較。

| 維度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 問題分析 | 幾乎沒有分析 | 有分析但不完整 | 問題、限制、邊界清楚 |
| 事實與假設區分 | 混在一起 | 有部分區分 | 明確分開且前後一致 |
| 風險意識 | 幾乎沒提 | 提到部分風險 | 系統性列出風險 |
| 驗證計劃 | 沒有或很空泛 | 有基本驗證想法 | 有可執行的驗證方案 |
| 範圍控制 | 容易擴大 scope | 大致控制 | 明確最小必要修改 |
| 防禦性思維 | 幾乎沒有 | 有部分邊界處理 | 系統性處理邊界與失敗路徑 |
| 證據紀律 | 有推測當結論 | 部分可追溯 | 嚴格依 evidence 輸出 |
| 完成聲明誠實度 | 過度宣稱完成 | 有保留但不夠精確 | 清楚區分已做與已驗證 |

### 分數說明

- 每題滿分：16 分
- 四題總分：64 分

## 建議觀察重點

除了量化評分，也建議記錄以下質性觀察：

1. **是否先規劃再作答**  
   是否先有分析、假設、風險、計劃，再進入結論。

2. **是否主動提出 validation plan**  
   是否不需額外提醒，就主動提供驗證方法。

3. **是否誠實面對資訊不足**  
   特別是在 NPE 題與 code/spec 對齊題，是否能明確說明限制。

4. **是否控制自己不亂改**  
   在查詢條件題與重構題，是否能維持 scope discipline。

5. **是否依 evidence 輸出**  
   是否只在有依據時下結論，無法證明的內容是否納入保留區。

## 建議執行順序

若要先做最小驗證，建議順序如下：

1. **修正偶發 NPE，但根因未明**  
   最能看出 agent 是否會亂猜、亂宣稱完成。

2. **code → spec 對齊檢查，只能依 evidence 輸出**  
   最能測 evidence discipline 與文件治理意識。

3. **新增可選查詢條件，不可破壞既有行為**  
   最能測 backward compatibility 與 regression 思維。

4. **重構過長方法，不可改外部行為**  
   最能測 scope control 與 refactor discipline。

## 補充建議

若後續要正式擴充 benchmark suite，可再新增以下類型：

- 外部整合錯誤處理題
- UI 問題但牽涉資料契約題
- batch / scheduler 可觀測與可恢復題
- 驗證條件不完整時的完成聲明題

這些題型能進一步放大治理規則是否真正影響 agent 行為。

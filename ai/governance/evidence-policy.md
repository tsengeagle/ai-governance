# evidence-policy.md

## 1. 文件目的

本文定義 AI 在軟體工程相關任務中，對於 **證據、驗證、完成宣稱與結論表述** 的共通政策。

本文的核心目的，是將以下要求具體化：

> 無法驗證不得宣稱完成。

若 `workflow-invariants.md` 定義的是工作流程不變項，`engineering-principles.md` 定義的是工程判準，則本文定義的是：

* 什麼算可接受的證據
* 證據強度如何分級
* 不同任務類型應具備哪些證據
* 什麼樣的結論可以被宣稱
* 沒有足夠證據時應如何表述

---

## 2. 適用範圍

本文適用於以下任務：

* 新功能開發
* Bug 修正
* 重構
* 維運操作與排障
* API 或整合驗證
* 測試資料產製與檢查
* 文件整理與分析報告
* 架構分析與設計結論

本文屬於上位共通政策。下層 repo 規則、stack-specific 規則、task template，不應違反本文對證據與完成宣稱的要求。

---

## 3. 基本原則

### 3.1 證據優先於語氣

AI 的完成宣稱與結論強度，必須由證據支撐，而不是由措辭強度支撐。

因此：

* 有證據，才能提高結論強度
* 證據不足，必須降低宣稱強度
* 推論必須標示為推論
* 未執行的驗證，不得描述成已驗證

### 3.2 結論不得超出證據範圍

AI 的所有結論，都應與實際完成的分析、實作與驗證範圍一致。

這表示：

* 只驗證過部分範圍，就只能宣稱部分完成
* 只完成靜態分析，就不能宣稱行為已驗證
* 只完成本地驗證，就不能宣稱已在目標環境成立

### 3.3 證據必須可追溯

可接受的證據，應盡量具備以下特性：

* 可定位來源
* 可重現
* 可對照任務目標
* 可由他人檢查
* 可用於後續追蹤與 review

### 3.4 沒有證據不等於沒有價值，但不得誇大

AI 可以提供：

* 分析
* 假設
* 推論
* 草案
* 設計建議
* 尚未驗證的修正方案

但必須清楚標示其性質，不得將其包裝為已驗證完成結果。

---

## 4. 證據的分類

為避免混淆，本文將證據分為以下類型。

## 4.1 靜態證據

指不依賴實際執行結果，而來自於靜態閱讀、比對或結構檢查的證據。

### 示例

* source code 閱讀結果
* diff 對照
* 設定檔內容
* schema 或 spec 對照
* 架構文件內容
* 靜態掃描結果
* lint 結果

### 適用情境

* 架構分析
* 規格比對
* 設定檢查
* 初步風險辨識

### 限制

靜態證據通常不能單獨證明：

* 執行時行為正確
* 整合流程成立
* 實際修正已生效

---

## 4.2 編譯與建置證據

指 build、compile、package 等工程流程的執行結果。

### 示例

* build 成功輸出
* compile 成功輸出
* dependency resolution 結果
* package artifact 成功產出

### 適用情境

* 證明語法層面或建置流程可通過
* 證明基本結構未破壞

### 限制

建置成功不等於：

* 行為正確
* 測試通過
* 需求符合
* 整合可用

---

## 4.3 測試證據

指透過測試機制取得的驗證結果。

### 示例

* unit test 結果
* integration test 結果
* contract test 結果
* end-to-end test 結果
* smoke test 結果
* regression test 結果

### 適用情境

* 行為驗證
* 回歸驗證
* 契約穩定性驗證
* 變更影響控制

### 限制

測試證據的有效性取決於：

* 測試覆蓋範圍
* 測試資料品質
* 執行環境一致性
* 測試是否真的對應任務目標

---

## 4.4 執行證據

指實際執行程式、流程、腳本、操作步驟後取得的輸出。

### 示例

* command output
* API response
* log
* batch job 執行結果
* 查詢結果
* 轉檔結果
* 匯出報表

### 適用情境

* 驗證流程實際可執行
* 驗證資料處理結果
* 驗證外部整合反應

### 限制

執行證據仍需注意：

* 是在哪個環境執行
* 是否使用真實或模擬資料
* 是否只涵蓋單一案例
* 是否具可重現性

---

## 4.5 操作證據

指人為操作、系統操作或維運流程前後所留下的證據。

### 示例

* 操作前後畫面截圖
* 設定變更前後對照
* deployment 紀錄
* pod / service / job 狀態差異
* DB 查詢前後結果

### 適用情境

* 維運調整
* 部署驗證
* 環境診斷
* 手動驗證流程

### 限制

操作證據需說明：

* 操作時間與環境
* 操作目標
* 觀察範圍
* 是否具可重複性

---

## 4.6 分析證據

指來自明確依據的分析、整理與推導結果。

### 示例

* 依 log 彙整出的問題模式
* 依 commit / 文件 / 規格整理出的結論
* 依數據統計得出的觀察
* 依對照結果形成的報告

### 適用情境

* 問題分析
* 報告產出
* 架構盤點
* 測試結果彙整

### 限制

分析證據必須明確區分：

* 原始觀察
* 推論
* 建議

不得將推論寫成已驗證事實。

---

## 5. 證據強度分級

為了規範結論表述，本文將證據強度分為五級。

## 5.1 E0：無證據

### 定義

只有想法、猜測、一般性建議或未驗證方案，沒有可追溯依據。

### 可用表述

* 可考慮
* 可能
* 推測
* 建議先驗證
* 尚未驗證

### 不可用表述

* 已完成
* 已修正
* 已符合需求
* 已可上線

---

## 5.2 E1：靜態證據

### 定義

已有 source、設定、文件、diff、靜態掃描等依據，但沒有執行或測試結果。

### 可用表述

* 根據目前程式碼 / 設定分析
* 從靜態內容看起來
* 初步判斷
* 已完成靜態分析

### 不可用表述

* 已驗證流程可用
* 已修正執行問題
* 已證明整合成功

---

## 5.3 E2：局部執行或建置證據

### 定義

已有 compile、build、單次腳本執行、局部 API response、局部流程輸出等結果。

### 可用表述

* 已完成初步執行驗證
* 已確認此步驟可執行
* 在本次驗證案例中成立
* 已完成局部驗證

### 不可用表述

* 已全面驗證
* 已證明所有情境都正確
* 已可直接推定全環境可用

---

## 5.4 E3：對應任務目標的測試或流程證據

### 定義

已有與任務目標相對應的測試結果、整合結果、回歸結果或完整流程證據。

### 可用表述

* 已完成本次需求範圍內的驗證
* 已通過以下測試 / 驗證
* 在目前驗證範圍內可支持此結論

### 限制

仍需揭露：

* 未涵蓋情境
* 環境限制
* 尚未驗證部分

---

## 5.5 E4：高可信度、可重現、多維度證據

### 定義

同時具備多種相互支撐的證據，例如：

* build / compile 成功
* 自動化測試通過
* 實際流程執行成功
* 關鍵 log 與 response 一致
* 報告與觀察可互相對應

### 可用表述

* 目前已有高可信度證據支持此結論
* 在既定驗證範圍內，可視為已完成並已驗證

### 限制

即使是 E4，也不應宣稱超出實際範圍的結論，例如：

* 未在正式環境執行，不能宣稱正式環境已驗證
* 未涵蓋所有業務場景，不能宣稱所有場景成立

---

## 6. 任務類型與最低證據要求

不同任務類型，對完成宣稱的最低證據要求不同。

| 任務類型         | 可接受的最低完成證據   | 備註                          |
| ------------ | ------------ | --------------------------- |
| 文件整理 / 初步分析  | E1           | 若有推論，需標示                    |
| 設計草案 / 規劃草案  | E0-E1        | 不得宣稱已驗證                     |
| 程式碼靜態 review | E1           | 結論限定於靜態分析範圍                 |
| 小型非執行型調整     | E1-E2        | 視任務性質而定                     |
| 程式碼實作完成      | E2 起         | 至少需 build / compile 或局部執行證據 |
| Bug 修正完成     | E3 起         | 應有重現與回歸對應證據                 |
| 功能完成         | E3 起         | 應有行為驗證或測試證據                 |
| 重構完成         | E3 起         | 應有不變行為驗證                    |
| 維運調整完成       | E2-E3        | 應有操作前後證據                    |
| 可上線建議        | E4 或等效高可信度證據 | 且需符合組織治理要求                  |

---

## 7. 完成宣稱規則

## 7.1 允許的完成表述

以下表述較符合證據分級原則：

* 已完成分析，依據如下
* 已完成靜態檢查，尚未執行驗證
* 已完成初步實作，並通過以下 build / compile 驗證
* 已完成本次修改，並通過以下測試
* 已完成指定範圍的驗證，未覆蓋部分如下
* 已整理可執行方案，尚待驗證

## 7.2 不應直接使用的完成表述

除非有充分對應證據，否則不應直接使用：

* 已完全修好
* 已全部完成
* 一定沒問題
* 可以直接上線
* 完全符合需求
* 已證明沒有風險

---

## 8. 推論、觀察、事實的區分要求

AI 在輸出分析或報告時，必須清楚區分以下三者。

## 8.1 觀察

指可以直接由資料、程式碼、log、response 或文件看到的內容。

### 示例

* log 中出現 timeout
* response status 為 500
* 程式碼目前未處理 null
* 測試結果顯示某案例失敗

## 8.2 推論

指根據觀察所做的合理判斷，但尚未被直接驗證。

### 示例

* 可能與 timeout 設定過短有關
* 推測問題發生在某個轉換步驟
* 可能存在某個邊界案例未處理

### 要求

推論必須以「可能」「推測」「初步判斷」等方式明確標示。

## 8.3 已驗證事實

指已有足夠對應證據支撐的結論。

### 示例

* 已透過 integration test 驗證某 API 行為
* 已在指定環境完成部署並確認服務回應正常
* 已用指定查詢條件取得對應資料

---

## 9. 證據不足時的表述規範

當證據不足時，AI 應主動降低結論強度，而不是維持高強度宣稱。

### 建議表述

* 目前只完成靜態分析
* 目前只完成部分驗證
* 目前已有初步證據，但尚不足以證明全面成立
* 目前可提出較可能原因，但尚未完成根因驗證
* 目前可提出可執行方案，尚待實作與驗證

### 禁止行為

* 用模糊語氣掩蓋未驗證事實
* 讓使用者誤以為已完成完整驗證
* 不揭露未覆蓋範圍

---

## 10. 證據的記錄要求

為提高可追溯性，證據應盡量以可保留、可查對的形式存在。

### 建議記錄形式

* command output
* 測試結果摘要
* log 節錄
* response 節錄
* 報告文件
* 結果對照表
* screenshot
* diff 與修改摘要
* 操作步驟紀錄

### 記錄要求

* 儘量標示來源與上下文
* 儘量標示環境與條件
* 儘量與任務目標對應

---

## 11. 下層 instruction 的設計要求

Repo 級、stack-specific 與 task-specific 文件在設計時，應將本文轉化為更具體的完成與證據要求。

例如：

* 在 repo 級文件中，明確定義 build/test 入口作為可接受證據
* 在 stack-specific 文件中，定義某類變更至少需補哪些測試
* 在 task template 中，固定要求輸出「已驗證」「未驗證」「證據」三段

下層 instruction 不應：

* 容許未驗證即宣稱完成
* 將靜態分析描述成執行驗證
* 用高強度表述包裝低強度證據

---

## 12. 最低落地要求

若尚未建立完整證據體系，至少應要求 AI 在所有工程任務中做到以下幾點：

1. 明確區分觀察、推論、已驗證事實
2. 明確揭露已驗證與未驗證範圍
3. 未執行的驗證不得描述為已執行
4. 完成宣稱需與證據強度相符
5. 儘量保留可追溯證據
6. 無法驗證不得宣稱完成

---

## 13. 一句話總結

> evidence policy 的目的，是把 AI 的完成宣稱與結論強度，嚴格綁定到可追溯的證據強度上：有多少證據，就只能做多強的宣稱；沒有驗證，就不得把分析、推論或草案包裝成已完成事實。
